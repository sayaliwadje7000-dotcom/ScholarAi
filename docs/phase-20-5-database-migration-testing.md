# Phase 20.5 — Database and Migration Testing

## 1. Objective

Phase 20.5 establishes automated validation for ScholarAI database
session management and Alembic migration integrity.

The purpose is to detect:

- Database session lifecycle defects.
- Missing rollback operations.
- Database session cleanup failures.
- Invalid migration references.
- Missing migration scripts.
- Duplicate migration revision identifiers.
- Broken migration history.

## 3. Database Session Testing

The session tests validate the existing application database
dependency.

Expected lifecycle:

SessionLocal()
     |
     v
Yield database session
     |
     v
Request execution
     |
     +------ Normal completion
     |            |
     |            v
     |          Close
     |
     +------ Exception
                  |
                  v
               Rollback
                  |
                  v
                Close

The tests verify that:

- A database session is yielded.
- Normal completion closes the session.
- Exceptions trigger rollback.
- Exceptions do not bypass session cleanup.
- Session creation errors propagate.
- The dependency does not commit automatically.

## 4. Migration History Testing

Alembic migration tests inspect the existing migration graph.

They validate:

- Alembic configuration.
- Migration directory availability.
- Migration head availability.
- Revision identifier uniqueness.
- Parent revision references.
- Migration source file availability.
- Basic migration graph traversal.

Multiple migration heads are not automatically treated as an error.
A project may intentionally have multiple branches or migration
heads. They should be reviewed and merged where appropriate.

## 5. Database Safety

These tests do not:

- Execute Alembic upgrade commands.
- Execute Alembic downgrade commands.
- Drop database tables.
- Modify production data.
- Change the configured database URL.
- Run destructive schema operations.

The existing opt-in database integration tests remain protected
by SCHOLARAI_RUN_DATABASE_INTEGRATION.

## 8. Migration Change Management

For future database schema changes:

1. Update the appropriate SQLAlchemy model.
2. Generate a migration using Alembic autogenerate.
3. Review the generated migration manually.
4. Verify upgrade operations.
5. Verify downgrade operations.
6. Run migrations against an isolated test database.
7. Execute database integration tests.
8. Verify migration history.
9. Commit the model and migration together.

Never assume that an autogenerated migration is correct without
reviewing its operations.

## 9. Completion Criteria

- Database lifecycle tests pass.
- Database failure tests pass.
- Migration history tests pass.
- Migration integrity tests pass.
- Existing database integration tests remain intact.
- Production database configuration remains unchanged.
- Full-suite regressions are investigated and resolved.

## 10. Scope Limitations

This phase validates database session lifecycle and migration
metadata integrity.

It does not yet execute migrations against a dedicated temporary
PostgreSQL database or validate every schema operation against
live database constraints.

Those validations require a dedicated isolated test database and
are separate from read-only migration graph inspection.
